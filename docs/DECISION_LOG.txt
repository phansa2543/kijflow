# DEC-001 — Phase 1 SaaS Foundation Scope

## Original Date

2026-10-07

## Revision Date

2026-10-10

## Decision

Phase 1 will build the minimum self-service SaaS Foundation required to support a real Organization and Membership lifecycle before the first Business Module.

Phase 1 must remain intentionally limited.

The goal is not to build a complete SaaS platform or enterprise account-management system.

## Context

The original DEC-001 established that Phase 1 should build only the minimum Foundation required before the first Business Module.

A later Product Foundation Review identified that the original scope was technically sufficient but did not fully represent the minimum lifecycle expected from a real self-service SaaS product.

The revised Product Model requires:

- global User Identity
- Membership between Users and Organizations
- self-service User registration
- self-service Organization creation
- Organization ownership
- minimum Membership lifecycle behavior

Billing, packaging, Business Modules, and enterprise functionality remain outside Phase 1.

## Problem

What is the minimum SaaS Foundation Kijflow needs before the first Business Module so that the system represents realistic SaaS identity, membership, ownership, security, and tenant behavior without introducing unnecessary complexity?

## Options Considered

1. Preserve the original minimal technical Foundation without adding real SaaS lifecycle behavior.
2. Expand Phase 1 into a broad SaaS platform including billing, advanced authorization, and enterprise account structures.
3. Expand only the Foundation concepts required for realistic self-service SaaS identity, Organization, Membership, ownership, and security behavior.

## Selected Option

Use option 3.

Build the minimum self-service SaaS Foundation required for a realistic Organization and Membership lifecycle while continuing to defer unrelated SaaS platform and Business Module functionality.

### In Scope

- Global Kijflow User Identity
- Organization
- Membership
- Self-service User registration
- Self-service Organization creation
- Authentication
- Trusted Organization context
- Minimum Membership lifecycle
- Invitation-based Membership onboarding
- Owner / Admin / Member Foundation authorization profiles
- Organization ownership protection and transfer
- Minimal capability-oriented authorization
- Strong tenant/data isolation
- Security and lifecycle behavior required to support the above

### Non-Goals

- Billing / subscription / package implementation
- Payment-provider integration
- Advanced permission builder
- Customer-defined roles
- Direct per-user permission overrides
- Complex approval hierarchy
- Enterprise SSO
- Teams / Departments without validated requirements
- Parent/subsidiary hierarchy
- Group-company hierarchy
- Consolidated multi-company reporting
- Shared inventory across Organizations
- Shared business data across Organizations
- Inter-company transactions
- Custom workflow engine
- Business Modules
- Production-scale DevOps platform
- Data-retention purge implementation
- Customer-offboarding export implementation

## Reasoning

A minimal SaaS Foundation must be small enough for a one-person software house while still representing real SaaS behavior correctly.

Identity, Membership, Organization ownership, and trusted tenant context are foundational concepts.

Deferring them until after Business Modules exist would make future changes materially more expensive across:

- data modeling
- authentication
- authorization
- tenant isolation
- APIs
- UX
- testing
- historical attribution

At the same time, Phase 1 must not expand into billing, multi-company ERP functionality, enterprise IAM, or speculative platform capabilities.

## Trade-offs

### Gains

- Foundation reflects realistic SaaS usage.
- A User can participate in multiple Organizations without duplicate identities.
- Tenant boundaries remain explicit.
- Membership and ownership lifecycle semantics exist before Business Modules depend on them.
- Future architectural migration risk is reduced.
- Self-service SaaS behavior is supported from the Foundation.

### Sacrifices

- Phase 1 identity and security modeling is more complex than the original one-User/one-Organization model.
- Additional lifecycle and security testing is required.
- Active Organization context must be handled deliberately.
- Phase 1 implementation scope increases moderately.

## Risks

- Membership and Organization switching may create tenant-isolation vulnerabilities if implemented inconsistently.
- Phase 1 could expand unnecessarily if future lifecycle concepts are treated as current implementation requirements.
- Owner semantics could become incorrectly coupled to future Business Module permissions.
- Foundation lifecycle logic could become too complex for one-person maintenance if unnecessary flexibility is introduced.

## Reversibility

Moderate.

## Reconsideration Trigger

Reconsider this scope if:

- implementation begins accumulating functionality not required for the accepted Foundation lifecycle,
- validated Business Module requirements reveal missing Foundation capabilities,
- or Foundation complexity becomes disproportionate to the needs of the first Business Module.

## Participants

- Founder
- Product Manager
- Tech Lead / Software Architect
- Engineering Mentor
- QA / Quality Engineer
- Command Center

## Founder Approval

Accepted

# DEC-002 — Phase 1 Identity, Organization, and Membership Model

## Original Date

2026-10-07

## Revision Date

2026-10-10

## Superseded Assumption

The original DEC-002 rule that one User belongs to exactly one Organization is superseded.

Organization remains the tenant/data-isolation boundary.

## Decision

For Phase 1:

- User represents a global Kijflow identity.
- Organization represents the SME/business using Kijflow.
- Organization is the tenant/data-isolation boundary.
- Tenant is not modeled as a separate business/domain entity.
- User and Organization are related through Membership.
- One User may have Memberships in multiple Organizations.
- One Organization may have multiple Memberships.
- A User may have at most one Membership for the same Organization.
- Memberships in different Organizations are independent.
- A User may exist with zero usable Organization Memberships.
- Team and Department are not part of the Phase 1 model.

Multi-Organization Membership does not imply multi-company business functionality.

## Context

The original DEC-002 intentionally selected a one-User/one-Organization model to minimize complexity.

The later Product Foundation Review established a real product requirement for:

- global User Identity
- participation in multiple Organizations
- independent Membership lifecycle
- self-service creation of additional Organizations

The original one-Organization assumption therefore became invalid.

Organization itself remains an appropriate tenant/data-isolation boundary.

## Problem

How should global User identity, Organization participation, and tenant boundaries relate while supporting real SaaS usage without introducing multi-company enterprise functionality?

## Options Considered

1. Keep one User permanently tied to one Organization.
2. Duplicate User accounts when the same person needs another Organization.
3. Use a global User Identity related to Organizations through Membership.
4. Introduce a higher-level Account/Tenant containing several Organizations.

## Selected Option

Use option 3.

Use global User Identity + Organization Membership while keeping each Organization as an independent tenant boundary.

## Conceptual Model

```text
User Identity
     │
     │ 0..N
     ▼
 Membership
     │
     │ N..1
     ▼
Organization
 = Tenant Boundary
```

## Membership Independence

Membership state in one Organization must not implicitly affect Membership in another Organization.

Examples:

- disabling Membership in Organization A does not disable Membership in Organization B,
- revoking Membership in Organization A does not revoke Membership in Organization B,
- leaving Organization A does not delete the global User Identity,
- a User may remain active in Organization B after leaving Organization A.

Organization manages Membership.

Organization does not own the User's global Identity.

## Membership Lifecycle Direction

Phase 1 product semantics must be able to represent:

- Pending
- Active
- Disabled
- Revoked / Former

The exact technical representation of invitation and Pending state is deferred to implementation design.

A Pending invitation does not require creation of an incomplete or fake global User Identity.

## Organization Context

Every tenant-scoped operation must operate within exactly one trusted Organization context.

A User may have access to multiple Organizations, but one tenant-scoped operation is always evaluated against one Organization boundary.

The exact technical representation of active Organization context is deferred to implementation design.

The architecture does not require a globally persisted `User.active_organization_id`.

## Security Constraints

- Client-supplied Organization identifiers do not independently establish trusted Organization context.
- Membership is security-sensitive.
- Normal access to an Organization requires a usable Membership.
- Membership lifecycle changes must not alter Membership in another Organization.
- Tenant-owned business data remains owned by exactly one Organization.
- Global User Identity must not be treated as belonging to whichever Organization is currently active.
- Pre-tenant access to Membership information must be explicitly constrained.

## Historical Identity

Revoking Membership must not destroy global User Identity.

Historical records may continue to identify a former member.

Historical attribution must not depend on the Membership remaining active.

## Non-Goals

This model does not introduce:

- parent/subsidiary hierarchy
- group-company hierarchy
- consolidated reporting
- shared business data across Organizations
- inter-company transactions
- shared inventory
- Teams
- Departments

## Reasoning

Global Identity + Membership reflects real SaaS behavior better than binding a User permanently to one Organization.

It supports:

- owners of multiple businesses
- consultants
- employees participating in different Organizations
- future SaaS use cases requiring the same identity in multiple Organizations

without introducing multi-company ERP semantics.

Organization remains a simple and understandable tenant boundary.

## Trade-offs

### Gains

- Identity is independent from Organization participation.
- Multi-Organization access does not require duplicate User accounts.
- Membership lifecycle becomes explicit.
- Leaving one Organization does not destroy unrelated access.
- Historical User identity remains stable.
- Organization remains a clear isolation boundary.

### Sacrifices

- Active Organization context becomes necessary.
- Organization switching introduces additional security paths.
- Authorization becomes Membership-specific.
- Membership lifecycle introduces additional data and testing complexity.

## Risks

- Stale Membership or Organization context could expose data if validation is weak.
- Developers could accidentally treat authentication as proof of Organization access.
- Membership discovery could become an unintended cross-tenant enumeration path.
- Duplicate or conflicting Membership state could create authorization ambiguity.

## Reversibility

Moderate to difficult once Business Modules depend on the model.

## Reconsideration Trigger

Reconsider if:

- Organization no longer represents the correct tenant boundary,
- one logical tenant must contain multiple business Organizations,
- group-company functionality becomes a validated requirement,
- or Membership semantics become insufficient for validated customer workflows.

## Participants

- Founder
- Product Manager
- Tech Lead / Software Architect
- Engineering Mentor
- QA / Quality Engineer
- Command Center

Accepted

# DEC-003 — Phase 1 Foundation Authorization Model

## Original Date

2026-10-08

## Revision Date

2026-10-10

## Superseded Assumption

The original two-profile model:

- Organization Admin
- Member

and the assumption that a distinct Owner profile was unnecessary are superseded.

## Decision

Phase 1 uses three Kijflow-defined Foundation authorization profiles:

- Owner
- Admin
- Member

The Foundation profile belongs to Membership context.

Each usable Membership has exactly one Foundation profile.

A User may therefore hold different profiles in different Organizations.

Organizations cannot create custom profiles or customer-defined roles in Phase 1.

Users cannot receive direct per-user permission overrides.

A configurable customer-defined Role entity is not required.

## Context

The original DEC-003 intentionally used only Admin and Member.

The Product Foundation Review introduced genuine Organization ownership semantics including:

- one Owner per Organization
- ownership transfer
- protection against Admin removal
- Organization lifecycle authority

This created a validated need for Owner in the Foundation authorization model.

Multi-Organization Membership also means authorization must be evaluated per Membership rather than globally per User.

## Problem

What is the minimum Foundation authorization model that supports ownership, administration, Membership-specific authority, and future capability-oriented Business Module authorization without introducing configurable RBAC?

## Options Considered

1. Keep Admin/Member and model ownership separately through ad-hoc flags.
2. Use Owner/Admin/Member as small Kijflow-defined Foundation profiles.
3. Introduce fully configurable Organization roles.
4. Introduce direct per-user permission assignment.
5. Build a generic authorization policy engine.

## Selected Option

Use option 2.

Use three small Kijflow-defined Foundation profiles:

- Owner
- Admin
- Member

Profiles exist within Membership context.

## Example

```text
Organization A → Owner
Organization B → Member
Organization C → Admin
```

## Owner

Owner represents Organization ownership and lifecycle authority.

An active Organization has exactly one Owner.

The Owner:

- must have an active Membership in the Organization,
- is established through trusted system-controlled behavior,
- has ownership/lifecycle authority,
- may transfer ownership,
- cannot be removed through ordinary Admin Membership management,
- cannot be disabled or revoked by ordinary Admin Membership management,
- cannot leave the Organization without first transferring ownership.

Owner does not represent universal Business Module authority.

Owner is not equivalent to:

```text
allow everything
```

## Admin

Admin represents Foundation administrative responsibility.

Admin may perform Foundation administrative actions according to explicit capability policy.

Admin:

- is scoped to the relevant Organization,
- cannot modify the Owner through ordinary Membership management,
- does not bypass tenant isolation,
- is not a universal Business Module superuser.

## Member

Member represents an ordinary Organization participant.

Member authority is determined by explicit capability policy.

## Authorization Scope

Authorization is evaluated within a specific Organization Membership context.

Authentication of a global User does not by itself grant authority inside any Organization.

Conceptually:

```text
Authenticated User
AND usable Membership
AND trusted Organization context
AND required authority
→ operation may proceed
```

## Authorization Principles

- Profile names are not universal authorization bypasses.
- Authorization remains capability/action oriented.
- Owner does not automatically inherit every possible capability.
- Admin does not automatically inherit every possible capability.
- Profiles are not assumed to form an implicit hierarchy.
- Tenant isolation remains independent from authorization.
- A Foundation profile never expands the tenant boundary.

## Lifecycle and Security Invariants

- An active Organization must have exactly one Owner.
- The Owner must have an active Membership.
- Arbitrary client input cannot grant Owner authority.
- Arbitrary client input cannot grant Admin authority.
- Foundation-profile changes are security-sensitive operations.
- Ordinary account/profile updates cannot elevate Foundation authority.
- Ownership transfer must not produce zero Owners.
- Ownership transfer must not produce more than one Owner.
- Ordinary Admin Membership-management operations cannot remove, disable, revoke, or demote the Owner.
- Once a privilege-reducing change takes effect in authoritative state, subsequent authorization decisions must no longer recognize the removed privilege.

## Non-Goals

Phase 1 does not introduce:

- customer-defined roles
- direct per-user permission overrides
- Sales Manager
- Inventory Manager
- Accountant
- configurable RBAC
- general-purpose ABAC
- generic policy engines

Future Kijflow-defined Business Module roles may be introduced only when validated Business Module workflows justify them.

## Reasoning

Owner now has validated Organization ownership and lifecycle semantics.

Using a small fixed set of Foundation profiles keeps the Phase 1 model understandable, testable, and maintainable.

Capability-oriented authorization prevents Owner and Admin from becoming universal future Business Module superusers.

## Trade-offs

### Gains

- Clear Organization ownership semantics.
- Small Foundation authorization model.
- Different authority per Organization is naturally supported.
- Owner lifecycle protection is explicit.
- No customer-facing RBAC complexity.

### Sacrifices

- Three profiles must be maintained instead of two.
- Ownership transfer introduces concurrency and lifecycle rules.
- Business Module authorization remains intentionally unresolved.

## Risks

- Developers may treat Owner as a universal superuser.
- Profile-name checks may spread through Business Modules.
- Ownership-transfer concurrency may produce invalid state if not enforced correctly.
- Owner/Admin capability mappings could grow excessively if Business Module concerns leak into the Foundation.

## Reversibility

Moderate.

## Reconsideration Trigger

Reconsider if:

- validated Business Modules need materially different authority structures,
- Organizations require customer-defined roles,
- per-user exceptions become common,
- segregation of duties becomes necessary,
- resource ownership becomes a frequent authorization dimension,
- contextual/workflow authorization becomes common,
- or Foundation profile mappings become too large or difficult to understand.

## Participants

- Founder
- Product Manager
- Tech Lead / Software Architect
- Engineering Mentor
- QA / Quality Engineer
- Command Center

## Founder Approval

Accepted

# DEC-004 — Phase 1 Permission Architecture

## Original Date

2026-10-08

## Revalidation Date

2026-10-10

## Decision

The core DEC-004 architecture remains accepted.

Kijflow uses a hybrid, capability-oriented permission architecture.

Capabilities are divided by responsibility:

- SaaS Foundation owns capabilities related to Foundation responsibilities.
- Business Modules own capabilities arising from validated business responsibilities and workflows.

Capability definitions and mappings are defined by Kijflow.

Organizations cannot create, modify, or override capability mappings in Phase 1.

Concrete Business Module capability catalogs remain deferred until their requirements are validated.

## Context

DEC-003 now defines three Foundation authorization profiles:

- Owner
- Admin
- Member

This changes the profile mappings used by DEC-004 but does not invalidate the capability-oriented architecture.

The capability architecture remains necessary to prevent Foundation profiles from becoming universal Business Module authorization rules.

## Problem

How should permissions remain secure, understandable, modular, and maintainable after introducing Membership-specific Owner/Admin/Member Foundation profiles?

## Options Considered

1. Abandon capabilities and authorize directly from profile names.
2. Preserve capability-oriented authorization and revise mappings for Owner/Admin/Member.
3. Introduce configurable RBAC.
4. Introduce direct per-user permissions.

## Selected Option

Use option 2.

Preserve the existing hybrid capability architecture and revise only the Foundation profile context and mappings.

## Revised Foundation Profile Context

Phase 1 Foundation capability mappings apply to:

- Owner
- Admin
- Member

Authorization is evaluated within the relevant Membership and Organization context.

## Authorization Invariants

- Every named capability must produce a deterministic outcome for every supported Foundation profile.
- An explicit grant authorizes a named capability.
- Absence of an explicit grant results in denial.
- Missing capability mapping results in denial.
- Unknown capability results in denial.
- Named capabilities fail closed by default.
- Owner does not implicitly bypass capability evaluation.
- Admin does not implicitly bypass capability evaluation.
- Foundation profiles are not assumed to form an implicit permission hierarchy.
- Capability mappings are explicit Kijflow-defined product/security policy.
- A capability never expands the tenant boundary.

## Capability Granularity

Capabilities should represent meaningful distinctions such as:

- administrative responsibility
- business responsibility
- security sensitivity
- materially different business consequences
- materially different audit significance

Capabilities should not mechanically mirror:

- CRUD operations
- API endpoints
- database tables

Two actions may remain separate capabilities even if their current mappings are identical when their business or security meaning differs.

Not every allowed action requires a named capability.

## Ownership-Specific Rules

Some genuine Organization ownership/lifecycle actions may use explicit ownership semantics.

Example:

- transfer Organization ownership

Ownership-specific rules must be:

- explicit
- intentional
- documented
- testable
- limited to genuine ownership/lifecycle behavior

Ownership semantics must not become a hidden bypass for Business Module capabilities.

## Baseline Authorization Rules

Some inherent Foundation behavior may exist without a named capability.

Such behavior must be:

- explicit
- intentional
- documented
- testable

Baseline behavior must never bypass a named capability protecting the same action.

## Capability Ownership

Every named capability must have a clear conceptual owner.

- Foundation capabilities belong to the SaaS Foundation.
- Business-specific capabilities belong to the responsible Business Module.

Cross-module/shared capability ownership remains deferred until module boundaries are established.

## Mapping Changes

Profile-to-capability mapping changes are security-relevant product changes.

- deny → allow is a privilege expansion
- allow → deny is a privilege reduction

Mapping changes require intentional review and regression validation.

## Entitlement Boundary

Module entitlement and User authorization remain separate concerns.

Conceptually:

```text
Entitlement
→ may this Organization use the module?

Authorization
→ may this Membership/User perform this action?
```

DEC-004 does not define:

- billing
- packaging
- subscription
- entitlement implementation

## Reasoning

The Product Model revision changes the Foundation profiles but does not invalidate capability-oriented authorization.

Capability-oriented authorization remains the primary mechanism preventing Owner/Admin semantics from becoming universal Business Module authority.

## Assumptions

- Owner/Admin/Member are sufficient for Phase 1 Foundation responsibilities.
- Kijflow defines authorization policy.
- Business Module requirements will define future module-specific capabilities.
- Default-deny behavior is preferable to accidental privilege expansion.

## Trade-offs

### Gains

- Existing authorization direction remains usable.
- Owner/Admin do not become automatic superusers.
- Authorization remains testable and explicit.
- Foundation and Business Module responsibilities remain separated.
- No customer-facing permission-configuration complexity is introduced.

### Sacrifices

- Three profile mappings must now be maintained.
- Future Business Module authorization still requires additional validated decisions.
- Mapping growth must be monitored carefully.

## Risks

- Capability catalogs may become too granular.
- Foundation may accumulate Business Module concerns.
- Profile-name checks may bypass capability architecture.
- Ownership semantics may become an informal bypass.
- Static mappings may become difficult to understand as modules grow.

## Deferred

This decision does not define:

- exact Sales capabilities
- exact capabilities for future Business Modules
- Business Module roles
- customer-defined roles
- direct per-user overrides
- shared/cross-module capability ownership
- record/resource-level authorization
- workflow/state authorization
- entitlement implementation

## Reversibility

Moderate.

## Reconsideration Trigger

Reconsider if:

- Foundation mappings become excessively large,
- validated Business Modules require materially different authority levels,
- Organizations genuinely require configurable roles,
- per-user exceptions become common,
- resource ownership becomes a frequent authorization dimension,
- contextual/workflow authorization becomes common,
- ad-hoc authorization flags accumulate,
- or entitlement and authorization become improperly coupled.

## Participants

- Founder
- Tech Lead / Software Architect
- QA / Quality Engineer
- Command Center

## Founder Approval

Accepted — Revalidated

# DEC-005 — Phase 1 Tenant Isolation Enforcement

## Original Date

2026-10-08

## Revalidation / Revision Date

2026-10-10

## Decision

The core DEC-005 architecture remains accepted.

Kijflow Phase 1 enforces tenant isolation through defense in depth on a shared PostgreSQL database and shared schema.

The enforcement model combines:

- trusted Organization context
- explicit application/service tenant scoping
- effective PostgreSQL Row-Level Security
- independently enforceable same-tenant relationship integrity
- fail-closed tenant semantics
- preservation of tenant ownership across derived storage boundaries

Organization remains the tenant/data-isolation boundary.

## Context

The original DEC-005 assumed that each authenticated User belonged to exactly one Organization.

Revised DEC-002 allows a global User Identity to hold Memberships in multiple Organizations.

This does not invalidate Organization-as-tenant or the defense-in-depth isolation architecture.

It changes how trusted Organization context must be established.

## Problem

How should Kijflow preserve strict Organization isolation when an authenticated User may legitimately belong to several Organizations?

## Options Considered

1. Trust Organization ID supplied by the authenticated User.
2. Bind each login session permanently to one Organization.
3. Establish Organization context only after validating the authenticated User's usable Membership.
4. Replace Organization-as-tenant with a higher-level tenant account.
5. Replace shared-database RLS architecture with separate databases.

## Selected Option

Use option 3 while preserving the accepted defense-in-depth architecture.

## Revised Context Establishment

Conceptually:

```text
Authenticated User Identity
        ↓
Organization selection intent
        ↓
Validate usable Membership
        ↓
Trusted Organization Context
        ↓
Application / service tenant scoping
        ↓
Effective PostgreSQL RLS
        ↓
Same-tenant relationship integrity
```

A client-supplied Organization identifier is selection intent only.

It does not independently establish trusted tenant context.

## Tenant-Isolation Invariants

1. Organization is the tenant/data-isolation boundary.

2. Tenant context derives only from trusted authenticated or trusted system state.

3. Arbitrary client Organization identifiers never independently establish tenant security context.

4. Missing, conflicting, ambiguous, stale, or untrusted tenant context fails closed.

5. Every tenant-owned resource resolves deterministically to exactly one Organization.

6. Derived tenant ownership is permitted only when mandatory, stable, unambiguous, deterministic, and simple enough to enforce consistently.

7. All normal Kijflow relational access to tenant-owned data remains subject to effective PostgreSQL RLS.

8. Any RLS-bypass execution context is privileged system context and cannot be selected, inherited, or used by ordinary tenant-facing execution.

9. Reused database execution context must never leak tenant identity between tenant-scoped units of work.

10. Application/service data access explicitly operates within trusted Organization context.

11. Read and write operations remain constrained to the trusted Organization.

12. Relationships between tenant-owned resources preserve same-Organization ownership.

13. Same-tenant relationship integrity must be enforceable independently of ordinary application caller discipline.

14. Rejected tenant-inconsistent mutations must not leave partially committed tenant-inconsistent state.

15. Ordinary application operations cannot reassign tenant ownership.

16. Owner never bypasses tenant isolation.

17. Admin never bypasses tenant isolation.

18. Owner/Admin status does not imply system-wide or cross-tenant authority.

19. Cross-tenant/system execution is a separate privileged security boundary.

20. Tenant-scoped non-request execution independently establishes trusted tenant context.

21. Every stored data/resource category receives deliberate ownership classification.

22. Missing or unspecified ownership never implicitly means global/shared.

23. Foundation/system/security data is classified according to actual semantics and is not automatically global.

24. Tenant ownership follows copies and derived representations across caches, files, indexes, exports, and other storage boundaries.

25. Tenant-isolation failures fail closed.

## Multi-Organization Membership Invariants

26. Every tenant-scoped operation operates under exactly one trusted Organization context.

27. A normal authenticated User must have a usable Membership in the selected Organization before trusted Organization context is established.

28. Disabled Membership cannot establish normal tenant access.

29. Revoked/Former Membership cannot establish normal tenant access.

30. Organization switching requires Membership validation for the destination Organization.

31. Stale Membership or stale Organization context fails closed.

32. Organization A tenant context must never be reused as Organization B context.

33. Membership revocation or access reduction must affect subsequent access decisions once authoritative state has changed.

34. A User's Membership-discovery path must not permit enumeration of another User's Memberships.

35. Pre-tenant Foundation operations must not expose tenant-owned Business Module data.

## Pre-Tenant Foundation Access

Some authenticated operations necessarily occur before trusted Organization context exists.

Example:

```text
Authenticated User
→ Which Organizations may this User access?
```

Such operations must use explicitly defined Foundation security rules.

They must only expose information the authenticated User is authorized to discover.

They must not become a generic cross-tenant data-access mechanism.

## Data Classification

Stored information must be classified according to actual ownership/security semantics.

### Tenant-Owned

Owned by exactly one Organization.

### Platform / Global

Intentionally global and not owned by a particular Organization.

Global User Identity is not owned by an Organization.

This does not make all User-related information globally readable.

### Foundation / Security

Classification depends on actual semantics.

Membership is Foundation security data associated with both a User and an Organization.

Access to Membership information must be explicitly constrained.

Missing ownership/classification is an architecture defect, not evidence that information is globally accessible.

## Authentication, Tenant Isolation, and Authorization

These remain separate gates.

Conceptually:

```text
Authenticated
AND usable Membership validated
AND trusted Organization established
AND target belongs to that Organization
AND required authorization capability granted
→ operation may proceed
```

Possessing a capability never expands the tenant boundary.

## Privileged System Execution

Legitimate system-wide or cross-tenant operations must use a separate privileged security boundary.

Such privilege must not:

- come from Owner status
- come from Admin status
- be selected through ordinary request parameters
- be activated through arbitrary Organization IDs
- be inherited accidentally from tenant-scoped execution

The exact privileged mechanism remains deferred.

## Threat Model Additions

Multi-Organization testing must explicitly consider:

- selecting an Organization without Membership
- disabled Membership attempting access
- revoked Membership attempting access
- stale context after Membership revocation
- switching Organization A → Organization B
- Organization-ID manipulation
- another User's Membership enumeration
- database-context leakage during Organization switching
- Owner attempting cross-tenant access
- Admin attempting cross-tenant access

## Maintainability Constraint

Tenant-isolation implementation should continue to favor a small number of standardized, repeatable patterns.

Multi-Organization Membership must not produce separate bespoke tenant-security mechanisms for every feature or module.

## Deferred Implementation Decisions

Milestone 3 now establishes authenticated global User Identity through the Founder-approved opaque server-side authentication-session design recorded in `PHASE_1_IMPLEMENTATION`.

That authentication session does not establish trusted Organization context.

DEC-005 still does not determine:

- exact RLS policies
- PostgreSQL roles
- `FORCE ROW LEVEL SECURITY`
- database tenant-context mechanism
- active Organization context representation
- exact relationship between authenticated global User session state and later trusted Organization-context representation
- FastAPI middleware design for tenant context
- connection-pool mechanics
- transaction mechanics required for tenant-isolation enforcement
- exact database structures required specifically for tenant-isolation enforcement
- exact database enforcement technique for ownership lifecycle beyond the approved Milestone 2 persistence invariants
- cache-key structure
- file/object-storage paths
- queue-message format
- search-index partitioning
- API `403` versus `404`
- privileged maintenance tooling

These remain implementation-design decisions for the relevant later milestone.

## Reasoning

Multi-Organization Membership changes trusted context establishment but does not invalidate Organization-as-tenant or the accepted defense-in-depth architecture.

The primary new requirement is proving usable Membership before establishing tenant context and safely handling Organization switching, disabling, and revocation.

## Trade-offs

### Gains

- Existing strong database isolation remains.
- Multi-Organization identity can coexist with strict Organization boundaries.
- Authorization and tenant isolation remain separate.
- Forgotten application predicates still have a database backstop.
- Security behavior remains explicit and testable.

### Sacrifices

- Context establishment becomes more complex.
- Pre-tenant Foundation access requires explicit design.
- Organization switching increases security-test scope.
- Database execution context remains security-sensitive.

## Risks

- stale tenant context
- stale Membership state
- tenant-context leakage through pooled connections
- incorrect RLS policies
- Membership enumeration
- unsafe Organization switching
- accidental Owner/Admin bypass
- incomplete ownership classification
- bespoke isolation behavior accumulating across modules

## Reversibility

Moderate.

## Reconsideration Trigger

Reconsider if:

- multi-company functionality requires shared tenant business data,
- customers require dedicated databases,
- regulatory requirements require physical isolation,
- tenant-specific data residency becomes required,
- RLS becomes operationally unmanageable,
- standardized isolation patterns cannot be maintained,
- or security review identifies bypass paths that cannot reasonably be controlled.

# DEC-006 — Business Module Independence Principle

## Date

2026-10-11

## Decision

Kijflow Business Modules follow a principle of functional and commercial independence with optional integration.

Each Business Module should be usable for its own core business workflow without requiring the customer to purchase or activate another Business Module.

A Business Module may depend on:

- the Kijflow SaaS Foundation,
- deliberately shared business concepts that are not themselves paid Business Modules,
- and explicit integration interfaces where cross-module workflows provide additional value.

Integration between Business Modules should enhance or extend functionality.

Integration should not be required merely to fill an essential gap in a module's own core workflow.

The default technical architecture for Business Modules is a modular monolith.

Module independence does not require independent deployment, independent databases, microservices, or distributed infrastructure.

## Context

Kijflow is intended to be a modular business-management SaaS.

The Founder wants customers to be able to use only the Business Modules relevant to them.

For example, a customer using Sales Management should be able to complete the core Sales workflow without being required to purchase Inventory, CRM, Accounting, or another Business Module.

At the same time, multiple modules should be able to integrate when the combined workflow provides meaningful business value.

The previous product direction established modularity but intentionally left the exact technical and commercial meaning of "module independence" unresolved.

The project also operates under a one-person software-house constraint.

A strict interpretation of independence could create unnecessary:

- duplicated data,
- duplicated business concepts,
- synchronization logic,
- integration complexity,
- operational overhead,
- and maintenance burden.

A practical boundary is therefore required.

## Problem

How should Kijflow define Business Module independence so that:

- customers are not forced to purchase unrelated modules,
- individual modules remain useful on their own,
- modules can still integrate,
- shared concepts do not become unnecessarily duplicated,
- and the architecture remains maintainable by one person?

## Options Considered

1. Make every Business Module completely self-contained, including duplicate copies of any data or concepts it needs.

2. Use functional and commercial module independence within a modular monolith, while allowing carefully chosen shared business concepts and explicit optional integrations.

3. Build a tightly coupled suite where Business Modules may routinely require other paid Business Modules.

4. Enforce technical independence through separate services, databases, deployment units, or a generic plugin architecture.

## Selected Option

Use option 2.

Kijflow will use:

- functional independence,
- commercial independence by default,
- clear module boundaries,
- carefully controlled shared business concepts,
- optional cross-module integration,
- and a modular-monolith technical architecture.

## Functional Independence

A Business Module must provide a coherent core workflow when used by itself.

Conceptually:

```text
Kijflow Foundation
        +
Selected Business Module
        ↓
Complete core workflow for that module
```

A Business Module must not require another paid Business Module merely to perform functionality that belongs to its own core responsibility.

Example principle:

```text
Sales Management only
        ↓
Core Sales workflow works
```

The customer should not be forced to purchase Inventory or CRM merely so Sales Management can perform its basic Sales responsibilities.

## Commercial Independence

Business Modules should be capable of being offered or entitled independently by default.

A customer should not be forced to subscribe to unrelated Business Modules merely because another module has a technical integration with them.

This decision establishes the commercial independence principle.

It does not determine:

- pricing,
- packaging,
- bundles,
- discounts,
- exact subscription mechanics,
- or entitlement implementation.

Those remain deferred.

A future validated business reason may justify a bundle or dependency, but such dependency must be intentional rather than an accidental consequence of technical architecture.

## Optional Integration

Business Modules may integrate when integration adds meaningful business value.

Conceptually:

```text
Module A
   │
   └──── optional integration ────→ Module B
```

Integration should enhance or automate workflows.

It should not repair an incomplete standalone module.

Examples of valid future integration may include:

- Sales triggering Inventory-related behavior,
- Sales sharing relevant customer context with CRM,
- Purchase affecting Inventory,
- Sales producing information consumed by Accounting.

These examples illustrate integration direction only.

They do not define the actual scope or ownership of those future modules.

## Shared Business Concepts

Business Modules may use deliberately shared business concepts where sharing is justified by actual domain requirements.

A shared business concept:

- is not automatically a paid Business Module,
- should represent genuinely shared business meaning,
- should prevent harmful duplication where appropriate,
- must have clear ownership and responsibility,
- must not become a dumping ground for unrelated functionality.

This decision does not yet determine which concepts belong in a shared business layer.

For example, Customer or Product/Service may later prove to be genuinely shared concepts, but their ownership must be derived from validated Business Module workflows rather than assumed in advance.

Do not create a large speculative Shared Core before those requirements exist.

## Technical Architecture

The default technical architecture for Business Modules is a modular monolith.

Conceptually:

```text
Kijflow Application
│
├── SaaS Foundation
│
├── Shared business concepts
│   └── only where validated
│
├── Sales
├── Inventory
├── CRM
├── Purchase
├── POS
└── Accounting
```

This means modules may exist within:

- the same application,
- the same deployment,
- and the same PostgreSQL system,

while still maintaining clear logical boundaries.

Module independence therefore does not mean deployment independence.

## Module Boundary Principles

Each Business Module should have:

- a clear business responsibility,
- deliberate ownership of module-specific behavior,
- deliberate ownership of module-specific data,
- understandable public/application interfaces,
- limited unnecessary coupling,
- explicit integration points.

One module should not directly depend on another module's internal implementation details.

Cross-module behavior should pass through deliberately defined boundaries.

The exact interface mechanism should follow validated workflow requirements.

## Integration Mechanism

This decision does not select one universal integration mechanism.

Depending on actual requirements, integrations may later use:

- direct application/service interfaces,
- internal APIs,
- domain/application events,
- or another sufficiently simple mechanism.

The simplest mechanism that preserves the required module boundary should be preferred.

Kijflow should not introduce:

- a generic event bus,
- plugin framework,
- message broker,
- service mesh,
- or distributed integration architecture

merely to satisfy an abstract definition of modularity.

## One-Person Maintainability Constraint

Module independence must reduce coupling without creating excessive operational or cognitive complexity.

For Kijflow, maintainability takes priority over architectural purity.

The design should favor:

```text
clear boundaries
+ one application
+ one operational model
+ deliberate integration
```

over:

```text
many services
+ duplicated concepts
+ synchronization
+ distributed infrastructure
```

unless future evidence justifies the additional complexity.

## Non-Goals

DEC-006 does not require:

- absolute independence between all concepts,
- duplicate Customer data per module,
- duplicate Product data per module,
- separate databases per module,
- microservices,
- separately deployed modules,
- generic plugin architecture,
- event-driven architecture for every integration,
- generic integration infrastructure,
- final shared-business-core design,
- final data ownership for Customer,
- final data ownership for Product/Service,
- final Sales module boundaries,
- final Inventory module boundaries,
- final CRM module boundaries,
- final commercial packaging,
- final pricing.

These remain subject to validated Business Module requirements.

## Reasoning

Strict technical independence sounds attractive but would create disproportionate complexity for a one-person software house.

If every module owned independent copies of common concepts, Kijflow would eventually need to solve:

- duplication,
- synchronization,
- conflicting source-of-truth data,
- integration failure,
- data reconciliation,
- and additional testing.

At the opposite extreme, tightly coupling every Business Module would undermine the modular product model and force customers to purchase functionality they may not need.

Functional and commercial independence inside a modular monolith provides a practical middle ground.

It allows:

- standalone customer value,
- optional integration,
- clear domain boundaries,
- lower operational complexity,
- and gradual architecture evolution based on real requirements.

## Trade-offs

### Gains

- Customers can adopt relevant modules without unnecessary module dependencies.
- Each module must provide meaningful standalone value.
- Cross-module integration remains possible.
- Deployment and operations remain simple.
- Shared concepts can prevent unnecessary duplication.
- Architecture remains practical for one-person development.
- Module boundaries can evolve from actual business workflows.

### Sacrifices

- Modules are not technically isolated deployment units.
- Some shared concepts may create controlled coupling.
- Clear ownership decisions will still be required as Business Modules are designed.
- Optional integrations introduce additional test combinations.
- Commercial independence may occasionally conflict with future validated business dependencies.

## Risks

- Shared business concepts may grow into an uncontrolled "shared everything" layer.
- Hidden coupling may develop between modules.
- A module may appear independent while depending indirectly on another module's implementation.
- Developers may duplicate data simply to preserve artificial independence.
- Too many optional integrations may increase testing and maintenance burden.
- Commercial packaging may later require exceptions to the default independence principle.
- Prematurely defining shared entities could lock Kijflow into incorrect domain boundaries.

## Guardrails

To control these risks:

- do not create shared concepts without validated cross-module meaning,
- do not make another paid Business Module a dependency without validated business justification,
- do not duplicate important business concepts merely to claim module independence,
- do not access another module's internals directly,
- do not introduce distributed infrastructure solely for modularity,
- prefer simple explicit integration mechanisms,
- validate module boundaries against real workflows.

## Reversibility

Moderate.

The modular-monolith implementation can evolve later if validated scale, operational, organizational, or isolation requirements justify stronger technical separation.

The commercial independence principle may also be revised for a specific module when validated business requirements demonstrate a genuine dependency.

Such exceptions must be deliberate and documented.

## Reconsideration Trigger

Reconsider this decision if:

- a validated Business Module cannot provide a coherent standalone workflow without another module,
- a genuine business dependency makes independent entitlement misleading,
- the shared business layer becomes excessively large or poorly owned,
- cross-module integrations become difficult to understand or maintain,
- module coupling prevents independent product evolution,
- scale or operational requirements justify independent deployment,
- regulatory or customer requirements justify stronger technical isolation,
- or the modular-monolith approach becomes materially harder to maintain than an alternative.

## Participants

- Founder
- Product Manager
- Tech Lead / Software Architect
- Business Domain Consultant
- Engineering Mentor
- QA / Quality Engineer
- SaaS / Business Strategy
- Command Center

## Founder Approval

Accepted

# DEC-007 — Post-Phase-1 Roadmap Skeleton

## Date

2026-10-15

## Decision

Kijflow adopts the following high-level roadmap skeleton after Phase 1:

```text
Phase 1 — SaaS Foundation
        ↓
Phase 2 — Module Enablement Foundation
        ↓
Phase 3 — First Business Module
          + Minimum Import / Export
        ↓
Phase 4 — Marketing & Growth Foundation
          + Build and publicly deploy the Kijflow Marketing Site
          + SEO / Content
          + Product Updates / News
          + Promotions
          + Contact / Feedback
          + Prepare capability for future genuine Customer Reviews / Stories
        ↓
Phase 5 — Commercialization & Launch
          + Production deployment of the Kijflow Business Application
          + Production API and PostgreSQL operating model
          + Production operations baseline
          + Pricing / Packaging
          + Billing / Subscription MVP
          + Customer Onboarding
          + Support Baseline
          + Final Launch Readiness
        ↓
        Paid Commercial Launch
        ↓
Phase 6 — Second Business Module
        ↓
Phase 7 — First Real Cross-Module Integration
```

This decision establishes the roadmap skeleton only.

Detailed phase scope, milestone decomposition, acceptance criteria, technical design, provider selection, implementation mechanism, and internal sequencing remain deferred until the relevant phase approaches.

## Phase 1 Protection

DEC-007 does not revise Phase 1.

Phase 1 remains governed by its already accepted:

- scope,
- architecture,
- milestones,
- implementation-level designs,
- security requirements,
- and acceptance criteria.

The post-Phase-1 roadmap must not be used to add the following into Phase 1:

- Module Enablement,
- Business Modules,
- Business Module Import / Export,
- Marketing & Growth functionality,
- production commercial operation,
- Billing / Subscription,
- or cross-module integration.

Phase 1 scope and architecture are therefore frozen against roadmap-driven expansion.

This does not prevent work required to satisfy already accepted Phase 1 requirements.

Security defects, correctness defects, tenant-isolation defects, regressions, or implementation behavior that violates existing Phase 1 requirements must still be corrected before Phase 1 can close.

## Context

Kijflow is being developed incrementally under a one-person software-house constraint.

Earlier accepted direction established that:

- Phase 1 should build only the minimum reliable SaaS Foundation,
- Business Modules should provide coherent standalone value,
- Module entitlement and User authorization are separate concerns,
- pricing, packaging, subscription mechanics, and entitlement implementation should not be prematurely encoded into Phase 1,
- cross-module integration should follow concrete workflows rather than speculative infrastructure,
- and complexity should be introduced only when justified by validated product, operational, or commercial needs.

Post-Phase-1 planning identified several materially different responsibilities that should not be treated as one undifferentiated effort:

- Organization-level Business Module enablement,
- creation of the first valuable Business Module,
- practical data import/export needed for adoption and portability,
- a public marketing and organic-acquisition surface,
- production deployment and commercial launch readiness,
- later standalone Business Modules,
- and real cross-module integration after concrete modules exist.

A high-level roadmap is therefore useful for sequencing these responsibilities without prematurely designing future phases.

## Problem

How should Kijflow sequence major post-Phase-1 work so that:

- Phase 1 remains protected from scope creep,
- Business Module enablement exists before commercial module packaging depends on it,
- the first Business Module receives focused product attention,
- practical data migration and portability are not ignored,
- marketing and SEO can begin before the paid commercial launch,
- the Marketing Site can operate publicly without prematurely exposing the Business Application to customers,
- Business Application production deployment and Billing / Subscription are completed as part of commercial launch readiness,
- additional modules remain independently useful,
- and real integration is implemented only after concrete participating modules exist?

## Options Considered

1. Keep only the previous broad sequence of SaaS Foundation followed immediately by the first Business Module and leave all later work unstructured.

2. Build Module Enablement, Business Modules, Marketing, production infrastructure, Billing, and integration together as one large post-Phase-1 effort.

3. Establish a staged roadmap separating Module Enablement, the first Business Module, Marketing & Growth, Commercialization & Launch, the second Business Module, and the first real cross-module integration.

## Selected Option

Use option 3.

Adopt the seven-phase roadmap skeleton while keeping Phase 1 unchanged.

## Phase 2 Direction — Module Enablement Foundation

Phase 2 establishes the minimum foundation required for Kijflow to know which Business Modules an Organization may use.

Conceptually, it separates:

```text
Module Entitlement
→ may this Organization use this Business Module?

Authorization
→ may this Membership/User perform this action?
```

Phase 2 is not the Billing / Subscription phase.

Its exact entitlement model, lifecycle, data structures, administration behavior, and interaction with Business Module authorization remain deferred to Phase 2 review.

The phase must not become a premature pricing, packaging, or subscription platform.

## Phase 3 Direction — First Business Module

Phase 3 delivers the first valuable Business Module as a coherent standalone workflow consistent with DEC-006.

The phase also includes minimum practical Import / Export capability where required for realistic adoption or useful portability of that module's business data.

Import / Export does not imply a generic ETL platform, arbitrary transformation engine, generic connector platform, or configurable data-integration framework.

The exact first Business Module boundary, workflow, capabilities, data ownership, Import / Export requirements, and acceptance criteria remain subject to product, domain, UX, architecture, and QA review.

This roadmap decision does not by itself finalize the detailed Sales Management / Managed Sales scope.

## Phase 4 Direction — Marketing & Growth Foundation

Phase 4 establishes Kijflow's public marketing, education, trust, feedback, and organic-acquisition surface.

The Kijflow Marketing Site is expected to be built and publicly deployed during Phase 4.

Conceptually:

```text
www.kijflow.com
→ public Marketing & Growth surface
```

High-level Phase 4 responsibilities may include:

- product and Business Module pages,
- SEO foundation,
- educational and domain content,
- product updates and development news,
- promotions,
- contact and customer-feedback channels,
- and structure for genuine future Customer Reviews / Stories when real customer evidence exists.

Because paid customer use does not begin before Phase 5, Phase 4 must not fabricate customer reviews, testimonials, usage claims, or customer evidence merely to fill marketing content.

Marketing & Growth must not expand into a speculative:

- general-purpose CMS,
- social network,
- customer community platform,
- marketing-automation platform,
- or high-volume low-value content operation

without later evidence justifying that complexity.

The exact repository structure, deployment topology, publishing mechanism, analytics tooling, and SEO implementation remain deferred to Phase 4 design.

## Phase 5 Direction — Commercialization & Launch

Phase 5 converts the developed product into a commercially operable SaaS offering and is the boundary before real paid customer use begins.

High-level Phase 5 responsibilities include:

- production deployment of the Kijflow Business Application,
- production deployment/operation of its required backend/API,
- production PostgreSQL operating model,
- production configuration and secret management,
- backup and restore capability,
- monitoring and error visibility,
- controlled deployment and database-migration procedure,
- recovery / rollback considerations appropriate to actual operational risk,
- production access control and operational security,
- pricing and packaging,
- Billing / Subscription MVP,
- required relationship between subscription state and module entitlement,
- customer onboarding baseline,
- support baseline,
- and final commercial launch review.

Conceptually:

```text
Phase 4
www.kijflow.com → public

Phase 5
app.kijflow.com + API + production data platform
        ↓
Commercial readiness
        ↓
Paid Commercial Launch
```

The exact production hosting provider, cloud architecture, payment provider, subscription lifecycle, pricing model, packaging model, deployment tooling, and CD policy remain deferred until Phase 5 review.

Production readiness does not imply enterprise-scale infrastructure.

Kijflow should continue to favor an operating model that one Founder can understand, deploy, monitor, recover, and support.

## Phase 6 Direction — Second Business Module

Phase 6 introduces the second Business Module as another coherent standalone workflow consistent with DEC-006.

The exact module is not finalized by this roadmap decision.

Current product/domain research may inform the choice, but validated customer value, business responsibility, workflow clarity, and one-person maintainability should drive the final selection.

## Phase 7 Direction — First Real Cross-Module Integration

Phase 7 implements and validates the first real integration between concrete Business Modules.

The integration must provide meaningful additional business value and must not repair an incomplete standalone module.

The exact integration workflow, trigger, ownership, consistency requirements, failure behavior, configuration, and implementation mechanism remain deferred until the participating Business Modules exist and their workflows are understood.

This decision does not authorize a generic integration framework, event platform, plugin system, or distributed architecture.

The simplest mechanism that preserves the required module boundaries should remain the default.

## Import / Export Principle

Import / Export is treated as a practical product capability rather than a standalone paid Business Module.

Where justified by the relevant workflow, it should support concerns such as:

- onboarding from existing tools,
- migration of existing business data,
- practical business-data portability,
- useful downstream analysis or operational use,
- customer trust,
- and future offboarding requirements.

Each Business Module should define Import / Export from its actual business semantics rather than from raw database tables.

Kijflow should prefer simple and explicit business-meaningful formats and workflows over a generic data-integration platform unless validated requirements justify greater complexity.

## Marketing Deployment Boundary

The Marketing Site and the Kijflow Business Application have different operational risk profiles and therefore do not need to share the same production-launch boundary.

Phase 4 may publicly deploy the Marketing Site because its primary responsibility is public content, acquisition, education, and communication.

The Business Application carries materially higher operational responsibility because it will eventually contain customer identity, Organization, and business data and support real operational workflows.

Its production deployment is therefore part of Phase 5 Commercialization & Launch rather than a requirement for Phase 4.

## Real Customer Use Boundary

DEC-007 does not establish a pilot or public free-trial period after Phase 3 or Phase 4.

There is currently no planned real-customer pilot before commercial launch.

Real paid customer use begins only after the required Phase 5 commercial launch criteria are satisfied.

A future decision may introduce trials or other acquisition models, but this roadmap does not assume them.

## Relationship to Existing Decisions

DEC-007 supplements rather than replaces DEC-001 through DEC-006.

In particular:

- DEC-001 through DEC-005 continue to govern Phase 1,
- DEC-006 continues to govern Business Module independence and optional integration,
- Module entitlement remains separate from User authorization,
- Business Module enablement does not itself determine pricing or Billing,
- shared business concepts remain subject to validated workflow evidence,
- and speculative generic integration infrastructure remains unnecessary.

If a later phase design conflicts with an accepted decision, the conflict must return to review rather than silently overriding that decision.

## Reasoning

The selected sequence deliberately moves from platform capability toward product value, acquisition, commercialization, and later expansion:

```text
Reliable Foundation
        ↓
Module Enablement
        ↓
First standalone customer value
        ↓
Marketing / acquisition surface
        ↓
Commercial and production readiness
        ↓
Paid launch
        ↓
Additional module value
        ↓
Validated cross-module value
```

This avoids two opposite mistakes:

1. building a large commercial/platform layer before there is a real Business Module to sell,
2. building a useful Business Module but postponing acquisition, production, billing, and operational readiness until after attempting to sell it.

The Marketing Site is separated from Business Application production because the two surfaces have different purposes and operational consequences.

Production deployment of the Business Application remains inside Commercialization & Launch because deploying customer-data infrastructure has little standalone business value if Kijflow is not yet preparing to accept real customers.

## Trade-offs

### Gains

- Phase 1 remains protected from future-roadmap scope creep.
- Post-Phase-1 work has a clear sequence without prematurely fixing implementation details.
- Module Enablement is separated from Billing / Subscription.
- The first Business Module receives focused attention before commercialization complexity is introduced.
- Import / Export is treated as an adoption and portability concern from the first Business Module.
- Marketing and SEO can begin before commercial launch.
- The public Marketing Site can accumulate visibility before the Business Application opens to customers.
- Business Application production work is performed in the same phase as the commercial systems and operational responsibilities that depend on it.
- Later Business Modules continue to follow the standalone-value principle.
- Real integration is deferred until concrete modules make its semantics knowable.

### Sacrifices

- Paid launch occurs only after several distinct post-Phase-1 capabilities are completed.
- A dedicated Marketing & Growth phase adds work before revenue begins.
- Import / Export may increase the first Business Module's delivery scope where it is genuinely required.
- Phase 5 contains several related but substantial commercialization and operational workstreams.
- Future evidence may require changing the roadmap before all phases are executed.

## Risks

- Phase 2 may accidentally expand into Billing or packaging design.
- Phase 3 Import / Export may expand into a generic data-platform project.
- Phase 4 may consume disproportionate Founder effort through content production or unnecessary marketing infrastructure.
- Marketing claims may get ahead of validated product capability if not reviewed carefully.
- Phase 5 may become overly broad if production infrastructure or Billing is over-engineered.
- Production requirements may be designed at enterprise scale despite the one-person operating constraint.
- Later Business Module priorities may change after real customer evidence appears.
- Optional integration combinations may eventually create excessive testing and support burden.

## Guardrails

- Do not add post-Phase-1 roadmap scope back into Phase 1.
- Do not redesign accepted Phase 1 architecture merely to anticipate a later phase without validated contradiction.
- Keep Phase 2 focused on minimum Organization-level module enablement rather than pricing or Billing.
- Keep Phase 3 focused on one coherent Business Module and only practical Import / Export justified by real adoption and portability needs.
- Keep Phase 4 focused on public acquisition, education, trust, feedback, and useful SEO/content capability.
- Do not publish fabricated Customer Reviews / Stories before real customer evidence exists.
- Keep Business Application production deployment within Phase 5 commercial readiness unless future evidence justifies a different boundary.
- Keep Phase 5 production architecture proportionate to actual operational risk and one-person maintainability.
- Do not introduce generic integration infrastructure before concrete integration requirements exist.
- Reassess future phases when validated customer, commercial, operational, or technical evidence materially changes their assumptions.

## Reversibility

High for the detailed contents and implementation of Phases 2 through 7 because DEC-007 intentionally establishes only a roadmap skeleton.

Moderate for the overall sequencing once substantial implementation begins in later phases.

Phase 1 remains governed independently by its accepted decisions and is not reopened by this roadmap.

# DEC-008 — Milestone 3 Password Minimum Length Policy

## Date

2026-10-15

## Decision

Milestone 3 changes the approved minimum password length from 15 to **8 Unicode code points**, evaluated **after Unicode NFC normalization**.

The approved M3 password-length and processing policy is:

- Minimum length: 8 Unicode code points after NFC normalization.
- Maximum length: 128 Unicode code points after NFC normalization.
- Accept Unicode and spaces, including leading and trailing whitespace.
- Do not trim, lowercase, casefold, or collapse whitespace in passwords.
- Reject passwords above the maximum; never silently truncate.
- Retain common/compromised-password blocklist screening.
- Retain Argon2id hashing and verification.
- Retain login and registration abuse protection, account-enumeration resistance, secure session handling, CSRF controls, and secret-leakage prevention.

The password-establishment sequence remains:

```text
raw password
  → Unicode NFC normalization
  → length / policy validation
  → common / compromised password blocklist evaluation
  → Argon2id hashing
```

Login applies the same Unicode NFC normalization before password verification.

Only the **minimum length** changes. DEC-008 does not expand Milestone 3 to MFA, Passkeys, Social Login, password recovery, email verification, or other authentication features outside its approved boundary.

## Context

The previously approved M3 implementation-level design required a minimum of 15 and maximum of 128 Unicode code points after NFC normalization.

During Founder implementation, password NFC normalization was completed before length/policy validation began. The Founder questioned whether a 15-code-point minimum imposed disproportionate self-service registration friction for Kijflow's intended simple SME product experience.

At the time of the handoff:

- Password NFC normalization was implemented.
- Latest full backend regression: 64 tests passed.
- Commit: `c6281e7`.
- GitHub Actions CI: PASS, confirmed by the Founder.
- Password length/policy validation had not begun.

This change revises an approved authentication-security requirement and therefore requires an explicit decision record and M3 implementation-plan synchronization.

## Problem

What minimum password length should Kijflow require for password-only self-service registration, given the trade-off between reducing user friction and limiting exposure to weak, guessable passwords?

## External Security Context

NIST SP 800-63B-4 states that passwords used as a single authentication factor SHALL be at least 15 characters. It permits a minimum of 8 when passwords are used only as part of a multi-factor authentication process.

Kijflow M3 is password-only, and MFA is outside its scope. The 8-code-point minimum is therefore an **intentional deviation from the NIST single-factor minimum**, not equivalent compliance and not a claim of equivalent security.

NIST also calls for Unicode code-point counting, and the retained controls include common/compromised-password screening and online-guessing protection. Argon2id and these other measures reduce important risks, but they do not make an 8-character password minimum equivalent to a 15-character minimum.

Official reference: https://pages.nist.gov/800-63-4/sp800-63b/authenticators/

Additional technical reference: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html

## Options Considered

1. Keep 15 Unicode code points as the minimum, preserving alignment with the NIST single-factor minimum but potentially imposing greater registration friction.
2. Reduce the minimum to 8, keep the 128 maximum and all approved security controls, and accept the lower password-strength floor.
3. Reduce the minimum while adding MFA to M3, improving authentication assurance but materially expanding scope, implementation, recovery, and support complexity.

## Selected Option

Use option 2: **8–128 Unicode code points after NFC normalization**, with all remaining approved M3 password and authentication security controls preserved.

## Reasoning

The Founder prioritizes reducing potential password-creation friction for Kijflow's self-service registration while maintaining the established M3 authentication architecture and security controls.

The concern that 15 characters materially harm Kijflow conversion is a reasonable product hypothesis, not a Kijflow-specific measured result. The known trade-off is that a shorter minimum allows a wider range of potentially guessable passwords. Founder approval explicitly accepts that risk instead of asserting security equivalence.

Adding MFA or another authentication mechanism solely to justify this minimum would expand M3 beyond its accepted boundary and create new maintenance and support obligations for a one-person software house.

## Impact Assessment and Validation

Command Center assessment of the approved M3 contract identified no necessary change to:

- Unicode NFC normalization or processing order;
- blocklist evaluation;
- Argon2id hashing/verification and parameters;
- credential persistence or atomic registration;
- session model and logout;
- account-enumeration resistance;
- login and registration abuse controls;
- tenant, Membership, or authorization boundaries.

Required regression coverage includes at minimum:

- 7 Unicode code points after NFC: reject;
- 8 and 9 code points after NFC: meet the length rule, but remain subject to other policy checks;
- 128 code points: meet the length rule, subject to remaining checks;
- 129 code points: reject;
- NFC canonical-equivalence behavior and inputs whose measured length changes after normalization;
- leading/trailing spaces preserved and counted;
- no silent truncation;
- blocklisted passwords rejected even if they meet length limits;
- Argon2id and abuse-protection paths remain intact.

This assessment does not claim independent sign-off from separately consulted Tech Lead or QA conversations. Any later specialist review that finds a material conflict should be escalated to the Founder before changing other accepted requirements.

## Trade-offs

### Gains

- Lower password-creation requirement for self-service registration.
- A simple, understandable minimum-length rule.
- No expansion of M3 authentication architecture or infrastructure.
- Retention of the existing password screening, Argon2id, and anti-abuse controls.

### Sacrifices

- Lower security floor for user-selected passwords relative to the approved 15-code-point policy.
- Intentional deviation from the NIST SP 800-63B-4 single-factor minimum.
- Increased exposure to weak 8–14-character choices that the previous rule would reject.

## Risks

- Some passwords that satisfy an 8-code-point minimum may remain relatively easy to guess, especially under offline attack following credential-hash exposure.
- Blocklists, Argon2id, and online rate limiting address different attack modes but do not fully offset reduced minimum password length.
- A future contractual, regulatory, or customer security requirement may require a stronger minimum or another authentication assurance model.
- Raising the minimum after real users exist will require deliberate treatment of credentials already established under the weaker policy.

## Reversibility

Moderate.

Before real customer credentials exist, the numeric minimum can be revised with limited operational impact. After customers have established 8–14-code-point passwords, changing the signup requirement alone would not strengthen their existing credentials; a separate transition or password-replacement policy would be required.

## Reconsideration Trigger

Revisit the decision if:

- security testing or abuse evidence exposes unacceptable risk under the shorter minimum;
- verified customer requirements, contractual obligations, or compliance targets require a stronger single-factor policy;
- measured Kijflow usability evidence shows little benefit from the lower minimum relative to the security cost;
- or a deliberate future authentication-assurance redesign changes the relevant trade-offs.

- Founder — decision and risk acceptance
- Engineering Mentor — Founder discussion/handoff
- Command Center — source-of-truth impact assessment and coordination

Separate Tech Lead / Software Architect and QA / Product Reviewer sign-off has not been independently documented in this decision record.

# DEC-009 — Milestone 3 Password Blocklist Strategy and Verification Gates

## Date

2026-10-16

## Founder Clarification Date

2026-10-17

## Decision

For M3 password establishment, select a two-stage common/compromised-password screening strategy:

1. Check the NFC-normalized password against a locally held, exact-match common-password list, using the selected SecLists `100k-most-used-passwords-NCSC.txt` during internal development, with applicable third-party rights confirmation required before external-user release.
2. Check the same normalized password against the HIBP Pwned Passwords Range API for known-compromised passwords.

Reject a password when either approved check positively identifies it as blocked. If the required HIBP check is unavailable or produces an unusable response, **fail closed**: do not establish the password by silently skipping the check. Report a generic temporary failure with a retry path, without leaking the password or internal screening details.

Keep a small Kijflow-owned screening boundary so the HIBP provider can be replaced by an appropriate alternative or local compromised-password checker. Do not introduce a generic plugin framework.

This decision establishes an implementation direction and quality/release gates. It **does not** certify third-party licensing, assert permission on behalf of HIBP or dataset owners, or modify DEC-008.

## Context

The approved M3 password-processing contract requires Unicode NFC normalization, 8–128-code-point length validation, common/compromised-password screening, and Argon2id hashing for password establishment.

The Founder is developing Kijflow as a **proprietary hosted SaaS** for SMEs. Kijflow customers use the service; Kijflow source code is not being sold or delivered to them. Kijflow is in internal development and has no external customer launch yet.

The Founder chose the local-list plus HIBP approach after reviewing implementation simplicity, security, third-party dependency, maintenance cost, and future replaceability. The Founder subsequently challenged the proposed blanket pause for license clarification and the assumption that mock API tests would replace real HIBP testing. The accepted approach separates technical development and testing from permission verification required before external-user availability.

## Problem

How can Kijflow meet its approved common/compromised-password screening requirement without depending only on mocks, tying its architecture permanently to one provider, or prematurely blocking internal development on commercial-launch questions?

## Options Considered

1. Local-only screening using an appropriately sourced and maintainable dataset; no external runtime dependency, but dataset coverage/update responsibility falls on Kijflow.
2. **Local common-password screening plus HIBP Pwned Passwords Range API**, with a replaceable provider boundary; added protection and live integration coverage, but an external availability and terms dependency.
3. External-provider-only screening; a simpler local footprint, but every screening request depends on the provider and the local fast-rejection layer is lost.

## Selected Option

Use option 2 provisionally for implementation, subject to the evidence-based gates below.

### Password Screening Contract

- Apply common/compromised screening to the NFC-normalized password **at password establishment**, after the already-approved length validation and before Argon2id hashing. Do not add breach-service calls to every login.
- Use exact-match local screening without trimming, lowercasing, case folding, or otherwise changing the approved password semantics.
- For HIBP Range lookups, hash the normalized password with SHA-1 solely for breach-data lookup. Transmit only the first five hexadecimal hash characters over HTTPS; compare the returned suffixes and counts locally. SHA-1 must not replace Argon2id credential storage.
- Do not transmit plaintext passwords, email addresses, or a full SHA-1 digest to HIBP. Request padded responses where supported (`Add-Padding: true`) and ignore padding entries with a zero occurrence count.
- Bound network timeouts and handle malformed data, network errors, and temporary service failures without exposing secrets or creating an uncontrolled retry storm.
- If HIBP cannot provide a valid required result, password establishment fails closed with a generic retryable error. This is a deliberate registration-availability trade-off.
- Keep the provider boundary minimal and replaceable without prematurely building an extensible framework.

### Development and Test Strategy

- **Internal development:** Engineering Mentor may guide implementation against the real HIBP API when the use is consistent with applicable current terms and normal operational constraints. External permission is not presumed merely because an endpoint is free.
- **Deterministic automated tests/normal CI:** use a mock/fake provider to test blocked/unblocked results, valid/invalid suffix data, zero-count padded entries, Unicode NFC behavior, timeouts, provider errors, fail-closed behavior, and absence of secret leakage. Normal tests do not need to contact HIBP.
- **Live integration tests:** separately test real HTTPS connectivity, the five-character SHA-1 prefix request, response parsing, and a known-compromised test case using test-only passwords. Complete and record a successful live integration test before closing the M3 blocklist subtask; repeat before exposing the feature to external users.
- **CI:** mocked tests remain the reliable push/pull-request gate. Live HIBP smoke tests may be manual or run in a separate explicitly invoked job; they are not required on every push. A real provider outage is not automatically a regression in Kijflow's own logic.
- Tests must avoid plaintext-password, token, and credential leakage in logs, traces, failures, and CI output.

### Third-Party and Release Gates

- **Internal Development — Local Dataset:** The Founder confirms that the selected SecLists NCSC password dataset may continue to be used and committed to the Kijflow development repository under the current internal-development approach. No additional owner confirmation is required solely to continue development or retain the existing Git commit.

- **Internal Development — HIBP:** Real HIBP Pwned Passwords Range API integration testing is permitted as part of the approved M3 development workflow, subject to applicable published terms and reasonable operational limits. Deterministic mocked tests remain the normal CI strategy.

- **Rights and Licensing Boundary:** Founder approval of the development approach is not a legal certification of third-party rights. Preserve applicable license notices and source attribution, respect known restrictions, and escalate any evidence of incompatible terms.

- **Git Repository:** The existing dataset commit was intentionally performed by the Founder. Its existence alone is not a repository discrepancy and does not justify Git history rewriting or remediation.

- **Pre-External-Release Verification:** Before making Kijflow available to external users, including a free beta or commercial launch, confirm the applicable dataset rights and HIBP commercial SaaS terms. Seek confirmation and guidance from the relevant maintainers, rights holders, or service provider where required. Unresolved incompatible terms must be addressed before release.

- **M3 Technical Acceptance:** Pending commercial-launch clarification must not automatically block internal M3 development or technical completion. M3 still requires a working password-screening implementation, deterministic tests, separate live HIBP integration validation, and Technical Security/QA review.

- **Dataset Strategy Changes:** Any material change to the approved local screening plus HIBP strategy, security coverage, or accepted maintenance trade-offs requires Founder review.

## Reasoning

This approach validates both Kijflow's deterministic internal behavior and its actual network integration without making every CI result dependent on HIBP uptime. A local common-password check can reject obvious choices quickly, while HIBP provides a separate known-compromised check. Separating screening behind a small adapter limits future migration cost for a one-person software house.

Separating internal development from external-user release avoids premature commercial-support processes while preserving the obligation to respect current third-party terms even during development.

## Trade-offs

### Gains

- Live API behavior is tested rather than assumed from mocks.
- Normal CI remains deterministic and can test error modes that are difficult to induce against a real service.
- Provider replacement remains feasible without rewriting registration.
- Commercial licensing uncertainty does not automatically suspend unrelated M3 coding.

### Sacrifices

- HIBP unavailability blocks new password establishment while the fail-closed policy applies, even if the local check passes.
- A local dataset adds provenance, update, and maintenance responsibility.
- Separate live integration testing requires deliberate execution and evidence before blocklist completion.

## Risks

- HIBP terms and commercial-SaaS permissibility remain unverified for Kijflow's intended future external use.
- The particular NCSC dataset's provenance and third-party rights require confirmation before external release. The existing Founder-authorized development commit alone does not establish a licensing violation or require Git remediation.
- The selected external provider can become unavailable or change its API/terms.
- Fail-closed behavior can temporarily prevent new user registrations and other password-establishment workflows.
- A common-password dataset may overlap with HIBP and prove insufficiently valuable for its maintenance cost.
- A passing live integration test proves connectivity/functionality, not contractual permission or future uptime.

## Reversibility

Moderate.

The provider can be changed behind the small screening interface, but data rights, matching semantics, test fixtures, availability behavior, and rollout must be re-evaluated. Changing from the selected two-stage approach requires Founder review when it alters the approved security behavior or accepted trade-off.

## Reconsideration Trigger

Revisit this decision if:

- verified HIBP terms do not permit the intended SaaS use;
- verified dataset rights do not permit the intended local-list use;
- real service reliability or latency makes fail-closed unavailability unacceptable;
- evidence shows negligible benefit from maintaining the local list;
- a suitable local/alternative compromised-password checker reduces cost or dependency while meeting the approved screening requirement;
- or a security review finds the privacy or failure handling inadequate.

## Participants

- Founder — choice of screening approach, test strategy, and risk acceptance.
- Command Center — technical/product trade-off challenge and source-of-truth synchronization.
- Engineering Mentor — implementation boundary and local dataset measurements as reported in handoff.

Independent Tech Lead and QA sign-off specifically for DEC-009 has not been recorded. Their future review must not be implied by this decision's acceptance.

## Founder Approval

Accepted on 2026-10-16 as the M3 implementation direction **with unresolved third-party/data-rights and release gates**. This is not third-party permission approval.

### Founder Clarification — 2026-10-17

Accepted.

The Founder reconfirms that the selected SecLists NCSC dataset may be used and committed during Kijflow internal development, and that real HIBP Range API integration testing may proceed under the published applicable terms.

Additional confirmation and guidance regarding commercial SaaS usage will be obtained from the relevant owners or providers before external-user release.

The intentional dataset Git commit is not, by itself, a reason to reopen repository investigation or rewrite Git history.

# DEC-010 — Phase 1 Functional Frontend Completion Requirement

## Date

2026-10-17

## Decision

Phase 1 must deliver the minimum browser-operable interface for all approved customer-facing SaaS Foundation workflows, connected to the real Next.js frontend, FastAPI backend, and PostgreSQL-backed application state.

Backend APIs, database behavior, and automated backend tests alone are insufficient to close Phase 1.

The frontend must remain a presentation and interaction layer. It does not become a second authority for authentication, trusted Organization context, tenant isolation, authorization, invitation binding, Membership lifecycle, or ownership invariants.

## Context

The Founder requires Phase 1 to conclude with a functional browser-based SaaS Foundation rather than an API-only foundation.

Product Manager and Product & UX Designer reviewed the minimum browser workflows.

The Founder approved Product Direction principles A–E.

Tech Lead / Software Architect and QA & Product Reviewer subsequently reviewed the proposal and issued PASS WITH CONDITIONS.

The technical and QA conditions are incorporated into this decision.

## Problem

How can Phase 1 deliver a usable, browser-operable SaaS Foundation without expanding into a complete commercial SaaS UI, duplicating backend security authority, or postponing frontend integration risks until Milestone 8?

## Options Considered

1. Complete only backend/API Foundation workflows and defer frontend implementation.
2. Complete backend milestones first and implement most frontend workflows in M8.
3. Implement the minimum frontend incrementally alongside M3–M7, with M8 consolidating integration, security, usability, and deployment validation.

## Selected Option

Option 3 — Incremental Minimum Functional Frontend.

### Product Requirements

- All approved customer-facing Foundation workflows must be operable through the browser without Swagger, Postman, or manual API requests.
- Use the minimum screens, dialogs, and reusable states required for coherent workflows.
- Screen count is guidance, not a fixed acceptance target.
- M3 provides registration, authentication, logout, and relevant browser states.
- M4 provides Organization creation, zero-Organization experience, selection/switching, visible current Organization, and a minimal application shell.
- M5 hardens Organization switching, stale context recovery, and tenant-aware frontend state.
- M6 provides authorization-aware actions and safe Access Denied behavior.
- M7 provides minimum invitation, Membership lifecycle, profile management, Owner protection, and ownership-transfer workflows.
- M8 consolidates browser E2E, security, usability, and deployment validation.

### Technical and Security Requirements

- FastAPI remains the authoritative security boundary.
- Next.js must not introduce an independent authentication system, frontend-owned JWT authority, or parallel session model.
- The frontend must support three conceptual states:
  - unauthenticated,
  - authenticated without trusted Organization context,
  - authenticated with trusted Organization context.
- These states do not require three separate visual layouts.
- Client Organization selection represents intent only; the backend must validate usable Membership before trusted Organization context exists.
- Current Organization visibility must reflect backend-recognized context.
- Frontend state/cache must remain isolated across Organization switching, identity changes, session expiry, logout, Membership changes, and authorization reductions.
- Stale or invalid security context must result in safe recovery.
- Hidden UI controls and frontend route guards never replace backend authorization.
- Cookie-authenticated state-changing Foundation workflows must satisfy applicable CSRF security requirements throughout M3–M7.
- Invitation acceptance must follow M7-approved identity-binding rules and cannot rely solely on unverified login-email equality.
- Ownership transfer must preserve backend-atomic exactly-one-Owner invariants.

### Testing and Closure

- Browser integration testing evolves incrementally with customer-facing workflows in M3–M7.
- A milestone introducing a customer-facing Foundation workflow is not complete until its minimum browser integration has been exercised against the real Kijflow backend.
- Core browser acceptance must exercise actual Next.js, FastAPI, and PostgreSQL-backed Kijflow state.
- External third-party services may use deterministic test doubles where appropriate in normal CI. Independent live integration requirements, including DEC-009, remain unchanged.
- Browser E2E supplements rather than replaces backend/PostgreSQL security, RLS, authorization, and concurrency testing.
- M8 must validate representative successful and adversarial Foundation journeys, including security-context changes and stale client-state recovery.
- The core browser journey must be exercised against the real non-production deployment.
- Phase 1 cannot close with unresolved browser integration defects that weaken accepted Foundation security behavior.

## Scope Exclusions

DEC-010 does not introduce:

- Business Modules
- Billing / Subscription
- Marketing Site
- generic analytics Dashboard
- generic Settings framework
- configurable roles or Permission Builder
- Teams / Departments
- speculative Design System infrastructure
- unrelated UI polish or convenience features

Exact routes, component design, frontend state library, API shapes, CSRF implementation mechanism, active Organization-context storage, and later-milestone persistence details remain deferred.

## Reasoning

An API-only foundation does not demonstrate that real users can complete the approved Foundation workflows.

Incremental frontend delivery exposes cookie, session, Organization-context, authorization, and integration failures earlier.

A minimum-screen strategy controls cost and complexity for a one-person software house.

Backend security remains independently testable and authoritative.

## Trade-offs

### Gains

- Real browser usability is validated before Phase 1 closure.
- Integration problems surface in the milestone where they originate.
- Security-context UX becomes testable.
- M8 remains a validation milestone rather than a large UI implementation phase.

### Sacrifices

- M3–M7 require additional frontend and browser-testing work.
- Each milestone has a broader completion gate.
- Browser security and state isolation add implementation and test complexity.

## Risks

- Frontend scope may expand into premature SaaS product polish.
- Client-side authentication or authorization may accidentally duplicate backend authority.
- Organization/User transitions may leak stale client state.
- Cookie/CSRF integration may behave differently in deployed environments.
- Excessive browser test coverage may increase maintenance cost.

## Reversibility

Moderate.

Exact UI composition and implementation mechanisms remain flexible, but removing browser-operable Foundation completion would change the accepted Phase 1 delivery requirement and require Founder review.
